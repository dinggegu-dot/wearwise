# 用户衣物图片的穿搭卡片：目标与对接

2026-11-06，用户要求将原 Project Plan 的图片穿搭输出补进技术设想并同步团队。该决定明确本轮需保留的产品目标；不代表已通过验收或已经发布。现有基础候选为 PR #21，实际代码状态和最新任务以 GitHub 为准。

## 用户看到什么

用户手动录入或经确认保存自己的单件衣物与照片，在推荐页选择天气和风格。系统根据真实衣橱生成最多两套组合，每套以一组并排/排列的衣物图片和名称组成**平面穿搭卡片**，附推荐理由；上衣＋下装＋鞋，或连衣裙＋鞋，寒冷时按规则加入外套。展示的是对应衣物保存的照片，而非模型创造的替代衣物。两套、单套、无法成套时按实际数据如实展示。

该目标是屏幕上可见的图片组合，不隐含生成可下载的合成图片、分享功能、虚拟试衣、自动抠图或新页面。不同拍摄背景可以保留，保持图片比例、不扭曲衣物；具体布局由 06 与 03/04 自主协商并适配手机。真实识别是独立环节：即使模型不可用，手动录入加图片也能进入衣橱并参与推荐；本决定不授权真实模型调用、费用或对外发送照片。

## 现有代码与技术路径

- #21 的 `src/modules/recommendation/ui/recommendations-page.tsx` 已遍历 `record.garmentSnapshots`，使用 `services.wardrobe.image(item.imageId)` 读取本地 Blob，通过 Object URL 在每件衣物名称上方显示，失效时释放 URL；未读取到图片显示“暂无图片”。这是源码核查，不代表新增的真实照片验收已通过。
- 衣橱记录持有真实的 `id`、`imageId` 等字段；图片单独存在 IndexedDB，UI 通过公开应用服务取得 Blob。推荐引擎只使用符合条件的已确认衣物并返回引用；UI 不直接访问数据库，不把图片编码或生成交给推荐算法。
- 示例如使用内置图片，须标注示例衣橱；真实模式必须读取当前衣橱已确认衣物对应的本地图片，不用示例或 AI 图片冒充。用户没添加图片时可以使用明确的无图占位，名称和推荐仍可读；图片读取失败也必须有可理解提示，不能出现其他衣物图片或伪造结果。
- 编辑/替换照片、删除、归档、排除、切换模式及并发变更，需要避免旧结果继续作为当前推荐。衣物变更后的结果何时失效、重生成与恢复由 02/05/06 对齐现有版本机制；图片资源的读写、错误和生命周期由 02/04/06 直接协商。需要显示历史结果时不得把过期内容当当前推荐；独立历史浏览不在本决定内。
- 资源只在本浏览器处理与读取；不要将用户图片传往模型或其他外部服务来制作卡片。详情请看 [Blob URL 生命周期](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob)。

## 验收：每项记录固定 SHA、操作与证据

1. 使用许可的、彼此明显不同的单件测试照片，通过真实衣橱录入并确认至少一件上衣、下装和鞋；从推荐卡逐一核对衣物 ID、名称和屏幕图片与衣橱一致。连衣裙＋鞋和冷天外套使用可重复的天气样本单独验证。
2. 未确认、归档、删除或排除的衣物不会出现在**重新生成**的组合；衣物照片替换后，重新生成显示正确的新照片，不能借用其他衣物的图片。
3. 刷新或同浏览器重开后，图片按本地保存状态可读取；无图片显示明确占位。注入图片读取失败时说明失败、名称仍可读，不破坏其他衣物/图片。
4. 数据不足时说明缺少的类别或可用衣物；只有一套就只显示一套。不同图片的比例正确，桌面与手机布局不重叠；文字/图片有可理解的名称。
5. 示例衣橱与真实衣橱隔离，示例图和示例天气明确标注；浏览器请求证据确认制作卡片过程不外传真实衣物照片。
6. 07 独立实测并留证；自动化结果、示例演示、真实照片联调及发布后复测分别记录。#21 目前已有 UI 代码但尚不能以示例图或现有测试推断上述所有条件已通过。

这些验收是本次明确目标的具体化，不删旧测试、不降低现有标准；最终候选合并与部署仍按用户决定和现有权限执行。
