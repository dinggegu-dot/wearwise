# 从任务到合并：团队最短流程

适用仓库：<https://github.com/dinggegu-dot/wearwise>。先到 [团队工作台](README.md) 找自己的编号和任务。角色工作台是长期入口；具体任务是单独的 Issue，确认 PRD、目标、验收、允许修改路径和上游依赖后再开发。当前成员还没有绑定账号，因此用 `[M02]` 等编号查找，不会自动显示在 GitHub 的“指派给我”列表。

## 成员：把代码交给 1 号

1. 登录自己的 GitHub，打开团队仓库，点击 **Fork** 创建自己的副本。每个人只需要 Fork 一次。
2. 在自己的 Fork 页面点击 **Code**，复制实际 HTTPS 地址。把下面的 `<你的 Fork 地址>` 替换成它；不要把尖括号原样输入终端。

   ```bash
   git clone <你的 Fork 地址>
   cd wearwise
   git remote add upstream https://github.com/dinggegu-dot/wearwise.git
   git remote -v
   npm ci --legacy-peer-deps
   ```

   `origin` 必须是自己的 Fork，`upstream` 是团队仓库。如果已经克隆，先检查远程地址，不要重复添加或覆盖。Node 需要 22.12 及以上。
3. 每项任务从已同步的 main 开新分支：确认 `git status` 没有会被覆盖的工作后，在自己的 Fork 页面 **Sync fork**，再执行 `git switch main`、`git pull --ff-only origin main`，最后 `git switch -c codex/issue-任务号-简短名称`。若有未提交内容、冲突或快进失败，先保存证据并联系 1 号，不运行 reset/强推。
4. 只修改任务允许的文件。在终端查看 `git status` 和 `git diff`，实际运行相关测试。将**具体文件路径**替换下面的占位符；不要直接复制尖括号，也不要用 `git add .` 扫入无关资料：

   ```bash
   git add <本任务的文件路径>
   git diff --cached
   git commit -m "说明本次完成的内容"
   git push -u origin HEAD
   ```

   如果 Git 提示登录，请使用 GitHub 支持的登录方式；不要把密码、Token、密钥、私人照片或数据写入代码、Issue 或 PR。公开仓库中的说明对所有人可见。
5. 打开团队仓库 [新建 PR](https://github.com/dinggegu-dot/wearwise/compare)，选择 **compare across forks**。核对目标为 `dinggegu-dot/wearwise` 的 `main`，来源是**自己的 Fork + 任务分支**。标题使用 `[M02] 描述结果` 等对应编号，填任务号、PRD 版本、测试结果和未验证项，点击创建。
6. 在自己的角色工作卡和具体任务中更新 PR 链接、状态、测试和阻塞。评审要求修改时，在**原分支**继续修改并推送，原 PR 自动更新，不必重新创建。

## 1 号：检查并由你决定是否合并

1. 打开 [待评审 PR](https://github.com/dinggegu-dot/wearwise/pulls?q=is%3Apr+is%3Aopen+-is%3Adraft)。先核对任务是否获批、目标 `main`、来源和作者。
2. 查看 **Files changed**：范围是否符合任务、接口是否冲突、是否包含不该公开的资料；再看 **Checks** 和提交者给出的实际测试与未验证项。绿灯只证明执行过的检查通过，不能替代业务验收。
3. 首次来自 Fork 的 PR，GitHub 可能要求仓库负责人批准运行工作流。先审查代码和工作流内容，再按页面提示批准；不要让不可信代码接触密钥。遇到冲突或失败，退回原分支修改并复测，不绕过检查。
4. 需求、代码和检查满足要求后，由仓库负责人在 PR 中决定是否点击 **Merge pull request** 并确认；合并是实际修改 `main`，并会触发公开网页的 Pages 发布。需要先协调 7 号验收的任务，不要提前合并。
5. 合并后在 [Actions](https://github.com/dinggegu-dot/wearwise/actions) 检查 Pages 工作流是否成功，再核对[公开网页](https://dinggegu-dot.github.io/wearwise/)。PR 合并、网页发布和业务验收是不同状态；如发布失败，在任务中记录并修复。

## 检查覆盖和权限

新增的 PR 检查在合入后生效：安装依赖、TypeScript、Vitest、Next.js 构建及现有 Chrome 端到端测试；当前无 Vitest 测试文件，使用 `--passWithNoTests` 仅允许零测试通过，不能宣称单元测试已执行；未来新增的测试失败仍会使检查失败。仓库目前未启用 main 分支保护，流程依赖 1 号人工把关；不要误认为已自动禁止直接推送。Fork 模式不授予成员团队仓库写权限。
