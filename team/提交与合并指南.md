# 从任务到 PR：把代码交到同一个产品里

当前共同任务是 [优化与最终交付 #10](https://github.com/dinggegu-dot/wearwise/issues/10)。先在 [团队入口](README.md) 找自己的具体任务并评论领取。

## 1. 准备自己的副本

没有主仓库写权限的成员先在 GitHub 点击 Fork。拥有者使用任务分支，不必 Fork 自己的仓库。每人只需克隆一次；下面的占位符要替换成自己的实际地址，不要原样复制尖括号。

```bash
git clone <你的Fork地址>
cd wearwise
git remote add upstream https://github.com/dinggegu-dot/wearwise.git
git remote -v
```

origin 是自己的 Fork，upstream 是团队仓库；已经存在时不要重复添加或覆盖。安装与启动按根目录 README，保留锁文件，不自行升级依赖。

## 2. 先核对基础候选，再同步 main

先检查 git status，保护已有工作；在 Fork 页面 Sync fork 后，再更新本地 main 并建任务分支：

```bash
git switch main
git pull --ff-only origin main
git switch -c codex/issue-任务号-简短名称
```

未提交内容、冲突或快进失败时先处理原因，不用 reset 或强推覆盖。#21 未合并时 main 仍为旧框架；按总计划核对固定候选，提前试用/设计，已批准的依赖开发须声明 #21/SHA，不能重复整包合并基础改动。#21 合入后同步最新 main。旧 A→B→C 顺序不再作为开工限制。

## 3. 开发、自测、直接交接

按个人卡与相关成员约定输入输出和负责文件。页面细节由执行者决定，沿用已有风格，无需逐项等 01 审批。接口可调用时提供分支/提交、例子和测试结果，对方接真实服务联调。

## 4. 提交自己的 PR

这是正式代码和交付文件的唯一通道。先按[工作流说明](工作流说明.md)填写任务、阶段、验收项和证据；[总览 #20](https://github.com/dinggegu-dot/wearwise/issues/20)从 PR 汇总，不需要再上传一份文件。

先看 git status、git diff，只加入本任务文件；不要把私人资料、图片或密钥上传。

```bash
git add <本任务的文件路径>
git diff --cached
git commit -m "说明这次完成的功能"
git push -u origin HEAD
```

打开 [新建 PR](https://github.com/dinggegu-dot/wearwise/compare)，选择 compare across forks；目标为 dinggegu-dot/wearwise 的 main，来源为自己的 Fork 和任务分支。标题以 [M01]—[M07] 对应编号开头。说明：任务号、当前阶段（兼容分类）、OPT 优化编号、设计、改动、真实测试、未验证项、依赖 PR、交给谁联调。

在具体任务卡放 PR 链接；返修在原分支继续提交，原 PR 会更新。不要提交 zip 代替代码差异，不要在多个工作卡重复维护进度。

## 5. 交完整候选版本给 07

A/B 段由 03、C 段由 06 汇总所需改动，提供在隔离分支可运行的候选版本、固定提交、相关 PR 清单和启动/测试方法。需要依赖未合并 PR 时与提交者确认引用的提交；不要直接覆盖别人的分支或 main。

07 实测后把问题交对应负责人，修复后在新提交复测。替身测试、单个模块通过、PR 检查绿灯，都不能替代完整业务联调。07 把阶段、提交、验收证据和遗留问题交 01。

## 6. 合并与发布

01 根据验收结果核对依赖、当前提交、冲突和自动检查；用户保留合并决定，实际操作须有权限和相应授权。来自 Fork 的工作流如需审批，维护者先查看改动再按 GitHub 提示处理。

获准后按依赖顺序合并，main 会触发 Pages 发布。07 复核合并后的完整流程，并查看 [Actions](https://github.com/dinggegu-dot/wearwise/actions) 和 [公开网页](https://dinggegu-dot.github.io/wearwise/)。失败交负责人修复，不绕过测试。
