# 从任务到 PR 和接力签收

先在 [总计划 #10](https://github.com/dinggegu-dot/wearwise/issues/10) 和自己的任务卡核对当前轮次，再读 [团队 AI 协作与交接指南](AI协作与交接指南.md) 与上一轮交接。第 02 轮从 [第 01 → 02 轮交接](https://github.com/dinggegu-dot/wearwise/blob/40d68d94a790e757143739fc84b05477f44d90ff/docs/handoffs/ROUND-01.md) 开始。

## 从固定候选建工作分支

具备团队仓库写权限的成员可使用团队任务分支，其余成员可用个人 Fork。先检查 `git status`，保护已有工作。使用 Fork 时，`origin` 是自己的仓库，`upstream` 是团队仓库；已有远端直接复用。

```sh
git status --short
git remote -v
git fetch upstream <上一轮交接分支>
git switch -c codex/round-XX-简短名称 <上一轮完整SHA>
```

示例里的尖括号为占位符；直接克隆团队仓库时使用 `origin`。按交接安装锁文件依赖和启动，先在本机验证交接，再修改。若 Git 找不到固定 SHA，先核对来源分支和实际提交。

## 提交和交接

用本仓库 PR 提交代码、测试和接口文档。按 [工作流说明](工作流说明.md) 保留模板字段，写清轮次、任务、起始与候选 SHA、依赖 PR、实测结果和接收人。同一成果返修推到原分支。记录真实服务、模拟异常和未执行项；提交内容不得包含密钥、私人照片或浏览器数据。

个人分支或 Fork 作为 PR 来源，目标按实际依赖选择。依赖已经在 `main` 的交付可向 `main` 提交；依赖尚未合入时写明候选分支和前置 PR，核对差异后选择正确目标，避免把前置成果算入本轮增量。接收方按固定 SHA 实际调用或操作后签收。 [新建 PR](https://github.com/dinggegu-dot/wearwise/compare) · [每轮交接模板](https://github.com/dinggegu-dot/wearwise/blob/40d68d94a790e757143739fc84b05477f44d90ff/docs/handoffs/ROUND-HANDOFF-TEMPLATE.md)

## 评审、合并与发布

持有写权限的组员可以评审、验收，并在 `main` 保护规则与必需 CI 满足后合并。第 10、12 轮由 07 主责独立整体验收；02 的电脑启动复验由 02 本人完成。Fork 检查如需批准，按 GitHub 提示处理。候选可先通过分支交接，合并和部署按实际授权另行处理。

`main` 更新会触发 Pages 发布。获准发布时记录合并后的 SHA、Pages 工作流结果和实际网页复测。类型、单测、普通构建、正式 Chrome 回归及静态检查分别记录，未运行写原因。 [GitHub Actions](https://github.com/dinggegu-dot/wearwise/actions) · [线上网页](https://dinggegu-dot.github.io/wearwise/)
