# WearWise 第一项任务：给团队和各自 AI 的协作指南

**团队协作指南。** 更新于 2026-11-05；任务及 PR 的最新状态以 GitHub 页面为准。功能范围以已确认的 [V0.3-r2 总计划](https://github.com/dinggegu-dot/wearwise/issues/10) 为准。本文解释怎样一起完成任务，不新增产品功能，也不替代各自任务卡。

## 一、大家共同完成什么

把当前三个页面的框架，逐步变成一个可以手动管理本地衣物、查看天气的 Demo。首页、衣橱、推荐页应看起来属于同一个产品。

按下面顺序做，每一段都是用户可操作、可单独验收的成果：

| 阶段 | 用户能做什么 | 主要合作 | 谁整理完整候选版本交 07 |
|---|---|---|---|
| A 手动衣橱 | 添加、查看、分类、编辑、删除衣物，刷新后保留；首页显示真实数量。没有照片时用占位图 | 02 提供存储；03 完成衣橱；06 完成首页数量 | 03 |
| B 本地照片 | 在已有表单选照片、预览、保存，刷新后仍能看到 | 04 提供本地处理；02 配合图片保存；03 接入原表单 | 03 |
| C 首页天气 | 在原首页选城市、查看真实天气；失败能重试或主动选择明确标记的示例 | 05 提供天气服务；06 接入原首页 | 06 |

上一段验收并合并后，下一段从最新 `main` 继续。后续负责人可以提前看代码、准备测试样本或研究接口，但不要各自开发另一套页面。遇到真正互不影响的工作，成员可自行协调，不必为了遵守顺序而空等。

本轮**不做** AI 识别、自动抠图、自动推荐、账户、云同步或社交。照片只在本地处理；天气只查询用户所选的六个城市。不把未来功能的占位界面说成已经可用。

## 二、给每个人和 AI 的共同工作规则

1. **先理解全流程，再看自己的任务。** 阅读总计划、个人任务卡、相关接口和实际 GitHub `main`；检查当前分支、未提交改动及已有实现。不要用本指南的状态快照代替最新代码。
2. **先对接，再分别做。** 找到下表中与你真正相关的人，在对应 Issue 或 PR 留下约定。不要等 01 号逐个传话；普通界面设计、交互、内部实现由相关成员自己决定，沿用现有风格。
3. **对外只通过公共接口。** UI 调用服务，不直接操作 Dexie；照片处理与最终入库分工明确。涉及公共文件时，先约定谁修改、什么时候交接，避免同时覆盖。
4. **用真实功能证明接通。** 可以先用测试替身做界面，但交付给别人时要说明哪些是真实实现、哪些是替身；不能把替身测试说成业务联调通过。
5. **从自己的 Fork 或获授权分支提交 PR。** 不直接覆盖主分支；不上传私人照片、密钥或用户数据。未经各自使用者授权，AI 不自行代替成员发送评论、提交、推送或合并。
6. **用事实报告。** 写明实际执行的命令和结果；没做的写“未执行”及原因。单元测试、真实 Chrome 操作、独立验收和线上发布分别记录。

## 三、谁必须和谁对接

| 对接 | 要确认的内容 | 双方怎么证明已经接通 |
|---|---|---|
| **02 ↔ 03** | 衣物字段、类别与保暖枚举；新增、列表、筛选、读取、编辑、删除、错误形式；从哪个分支/提交调用 | 03 用 02 的真实服务跑“新增→刷新→编辑→删除”，双方记录所测提交和结果 |
| **02 ↔ 06** | 数量如何读取，回到首页时何时重新读取 | 新增两件显示 2，删除一件并回首页显示 1；不是写死或假数据 |
| **03 ↔ 06** | 三页导航、现有按钮、卡片、字体、颜色和间距；谁在何时修改共享入口 | 同一候选版本从首页进入衣橱再返回，数量正确，手机和电脑视觉一致 |
| **04 ↔ 03** | 接收的文件、处理成功返回什么、失败怎样展示、预览资源何时释放 | 在原表单选择正常图片能预览；取消和异常文件不会创建衣物 |
| **04 ↔ 02** | 处理后的 Blob 怎样交给存储；无图占位、保存失败、图片引用及删除 | 确认后保存，刷新能读取；失败无半条记录，删除不误删其他衣物引用的图片 |
| **05 ↔ 06** | 城市输入、温度/体感/时间/示例标记、错误和重试；快速切换时如何避免串城 | 在首页用真实服务切换城市，验证失败重试和主动示例；记录真实网络与模拟测试各自结果 |
| **03 / 06 ↔ 07** | 候选版本包含哪些 PR、固定提交、启动方法、验证步骤、已知问题 | 07 能从给定提交启动并复现；发现问题直接交对应负责人，修复后按新提交复测 |

**对接记录模板：**双方直接在对应任务卡或 PR 中记录；只有需要对接的两个人参与即可。

```text
参与人：02 / 03
阶段与目的：A 段，表单保存和显示衣物
可调用的分支 / PR / 固定提交：
入口和输入：
成功返回例子：
失败时怎样提示：
各自负责修改的文件：
提供方自测结果：
使用方已确认 / 待确认的问题：
双方真实联调的操作、提交和结果：
```

写“可联调”意味着代码、固定提交、调用例子和自测结果已提供；**不等于对方已经联调成功**。没有收到对方确认时，在任务中标明等待谁和缺什么，不要擅自假定接口已确定。

## 四、七位成员各自做什么

### 01：让工作顺畅，而不是审批所有细节

维护当前阶段、解决成员无法自行解决的阻塞，查看 07 的验收结论并按用户决定和实际权限处理合并。记录合并及发布结果；不为凑代码另造任务，不做每张草图的审批人。[01 任务](https://github.com/dinggegu-dot/wearwise/issues/11)

### 02：本地衣物与图片存储

A 段交付衣物服务、事务、占位图及测试，与 03 对齐操作、与 06 对齐数量；B 段与 04、03 对接 Blob 和图片引用。负责给出可运行提交与调用例子，配合真实浏览器验证，不独自宣布整段完成。[02 任务](https://github.com/dinggegu-dot/wearwise/issues/12)

### 03：衣橱体验与 A/B 段完整交接

A 段在现有页面完成表单、列表、详情、分类、编辑、删除和各状态，接入 02 的真实服务，并与 06 对齐首页数量和共用样式。B 段在同一表单接入 04 的照片处理和 02 的保存。整理完整候选版本和依赖清单给 07；不必替其他成员包揽底层代码。[03 任务](https://github.com/dinggegu-dot/wearwise/issues/13)

### 04：本地照片处理

可提前准备样本与方案；B 段从最新主分支开始，与 03 约定选择、预览和错误，与 02 约定 Blob 保存。支持 JPEG、PNG、静态 WebP；输入不超过 10 MB、处理后最长边不超过 1600 px；不支持 SVG、动图和 HEIC。不另做独立衣橱页面。[04 任务](https://github.com/dinggegu-dot/wearwise/issues/14)

### 05：天气数据服务

可提前查看现有代码和准备测试；C 段与 06 对齐城市、温度、体感、时间、异常、重试及示例标记。六城市为深圳、广州、上海、北京、成都、杭州。真实请求与模拟测试分开记录；不独立再做一个天气页面。[05 任务](https://github.com/dinggegu-dot/wearwise/issues/15)

### 06：首页体验与 C 段完整交接

A 段用 02 的服务展示真实衣物数量，与 03 统一视觉并把改动交给 03；C 段将 05 的天气接进原首页，处理加载、失败、重试和主动示例。整理真实服务与界面的完整候选版本给 07。推荐功能仍明确标记未开放。[06 任务](https://github.com/dinggegu-dot/wearwise/issues/16)

### 07：独立验收完整行为

从一开始准备验收用例。A/B 从 03、C 从 06 收到候选版本后，记录固定提交、执行环境、测试及结果；用本机正式 Chrome 的隔离环境实测流程、异常和手机布局。问题交对应负责人修复，复测后把证据和未验证项交 01；合并后复核主分支和网页。[07 任务](https://github.com/dinggegu-dot/wearwise/issues/17)

## 五、M02 已交出的实际接口：A 段从这里开始

截至 2026-11-05，M02 `walkercell` 在 [PR #19](https://github.com/dinggegu-dot/wearwise/pull/19) 提交了第一版数据服务，固定提交 `1b9891de89b87a4f7dbab1a2fc77cc7daf56d10a`；**PR 尚未合并。** [M02 的调用表与示例](https://github.com/dinggegu-dot/wearwise/issues/12#issuecomment-6657123752)目前是供 03 确认的交接提案，不应假装双方已确认或已联调。

M02 提案包括 `wardrobe.add`、`list`、`get`、`update`、`remove`、`image` 和 `count`；类别使用 `top / bottom / outerwear / dress / shoes`，保暖使用 `light / medium / warm / unknown`。新增时支持同一次提交使用同一个 `requestId` 防重复。03 应核对实际 PR 代码、输入输出及错误，直接向 02 提出问题；06 与 02 确认首页如何读取和刷新数量。M02 评论中提到“模式由 1 号装配决定”属于待双方核对的说法，不应理解为所有实现必须等待 01 审批。

**避免 02 和 03 互相等待：** M02 评论写的是“等 03 接好页面后再标可联调”，而 03 的任务曾写“收到可联调交付后才接入”。这里统一区分两个状态：①“接口已提供、可以开始联调”只要求 02 提供代码、固定提交、调用例子和自测结果，03 可据此读取 #19 并开始接入；②“双方联调通过”必须等 03 接好页面、双方实测后才记录。03 不必等待第二个状态才开始工作；双方尚未确认或未运行的部分仍如实保留。

M02 在 PR 中报告了本地类型检查、7 项 fake-indexeddb 测试、构建和 2 项 Chrome E2E 通过；这些是**提交者报告**，不是本文独立复测结论。PR 页面此前显示 Fork 工作流等待维护者批准；实际状态以 GitHub 当时页面为准。真实 Chrome 的衣物页面持久化及与 03、06 的完整联调仍待执行。

若 03 需要在 #19 合并前开始联调，应明确基于其 Fork 分支及固定提交建立自己的隔离候选分支，并在自己的 PR 写清依赖 #19；不要把尚未合并的接口当作已存在于 `main`。固定提交发生变化时，双方重新核对并重测受影响内容。

## 六、一段怎样交付，才不会到最后才发现拼不上

1. 提供方提交可运行代码和自测结果，标出具体分支与提交；直接请使用方核对调用表。使用方确认或提出具体修改。
2. 各成员把自己的 PR 关联任务卡，写明依赖。03 在 A/B、06 在 C 整理包含相关改动的**隔离候选版本**；注明候选分支、固定提交、来源 PR 与对应提交、启动命令和演示步骤。不要覆盖别人的分支或主分支，也不要让 07 猜该合并哪些内容。
3. 主负责人先用真实服务自测完整用户流程，注明未验证项，再交 07。07 实测并反馈给相关成员；修复会改变提交，须记录新提交并重新验证受影响内容。
4. 07 提供“通过 / 失败 / 未执行 / 阻塞”及证据。01 根据验收、依赖和用户的合并决定处理合并；合并后 07 回归主分支，检查网页发布。未具备权限的成员不能因为任务卡写了流程就获得权限。
5. A 完成后再把 B 建立在新的主分支上；B 完成后再做 C。不得为通过而删掉或跳过失败测试；如果旧测试只覆盖禁用状态，应按新功能更新，同时保留必要覆盖。
