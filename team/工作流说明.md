# 一条提交通道，一份进度总览

**正式交付只走 [dinggegu-dot/wearwise 的 PR](https://github.com/dinggegu-dot/wearwise/pulls)。** [新建 PR](https://github.com/dinggegu-dot/wearwise/compare) · [自动汇总 #20](https://github.com/dinggegu-dot/wearwise/issues/20) · [目标及任务 #10](https://github.com/dinggegu-dot/wearwise/issues/10)

产品仍是 V0.3-r2 的 A 手动衣橱 → B 本地照片 → C 首页天气；这次只配置交付管理，不改变七人的职责或产品范围。

## 成员只需要怎么做

1. 在 #10 找自己的 #11—#17 任务；已有分支和 PR 就继续使用。第一次提交按[操作指南](提交与合并指南.md) Fork、建分支、推送。
2. 向主仓库 `main` 提 PR，标题以本人编号 `[M02]` 这样的格式开头。可以先开 Draft PR，方便别人看到接口和进展。
3. 填 PR 模板最上面的字段：**具体任务、当前阶段、验收项、交付状态、基线和依赖**。写明哪个用户行为已实现、测试证据和未做的部分。已有 #19 不重开、不重做；作者在原 PR 补充这些字段即可。
4. 代码、测试、接口说明和需长期保存的验收报告，都提交到这个 PR 的分支。返修继续推送该分支，原 PR 自动更新。不要另发 zip、私聊文件，或直接向主仓库 main 上传。
5. 交接给实际合作人，在原 PR 评论写明“已更新，当前提交是……，下一步请……”。修改描述、结束验收、关闭未合并 PR 等没有触发 CI 的变化，也可用该评论触发汇总。评论不需要重复粘贴代码。

一个具体交付用一个 PR；同一成员可分 A/B/C 提多份小 PR。03/06 的整段候选也是 PR，在正文列出来源 PR 和固定提交，明确是联调候选；不把多个副本当独立交付，也不同时合并重复的改动。个人 PR 依赖未合并代码时先写清依赖，合并顺序由实际依赖决定。

### 一个填写例子（不是 M02 的验收结论）

```text
标题：[M02] A 段衣橱数据服务
具体任务：#12
当前阶段：A 手动衣橱
验收项：A02、A03、A06、A07
交付状态：接口已提供可开始联调
基线提交：实际 SHA
依赖 PR / 固定提交：无
```

正文按每条目标写证据，例如“A02 只提供 count 服务；首页接入与刷新后的真实数量验证待 06 完成”。不要照抄示例的验收项或状态。

## 07 怎么验收，01 怎么接收

07 在 03（A/B）或 06（C）的候选 PR 中记录：候选完整 SHA、包含的来源 PR/SHA、环境、A01—A08 中本阶段相关项的 PASS / FAIL / NOT_RUN / BLOCKED、操作与日志/截图、问题交给谁。可提交正式 GitHub Review，详细结果过长时放仓库验收文档并链接；完成后在同一个 PR 评论“验收记录已更新”触发采集。验收身份必须核对实际账号，不能因为标题写 M07 就相信。

01 从 #20 查看谁交了什么，打开候选 PR 核对 07 的证据、依赖和当前提交；不用替每个人拼文件。用户决定是否合并。合并后 07 复测 main 与网页，把实际 SHA、Pages 运行链接、网页结果写回候选 PR。若代码又有更新，旧 SHA 的结论不能直接沿用。

**“已提交”“可联调”“联调完成”“07 验收通过”“已合并”“网页已验证”是不同状态。** 前三项由成员附证据声明；后续须核对独立测试、合并记录与真实网页。总览不自动把任务勾成完成，不用通过数计算完成率。一个 PR 合并也不自动关闭跨 A/B 的个人总任务；避免随手写 `Closes #12`。

## 总览自动做什么

- 从 GitHub API 读取本轮所有 PR（从 #18 起，包含未编号 PR、草稿、关闭和已合并），展示真实提交账号及标题声明的角色。
- 根据 PR 的固定字段关联个人任务与 A01—A08。缺项、旧模板或编号不一致会提示，不悄悄推断完成。
- 收集文件清单、增删数量、固定提交、当前提交检查、Actions、正式评审及其提交版本。每份 PR 显示前 20 个文件，全部差异通过原 PR 查看；不下载运行成员代码，不自动复制进 main。
- 读取当前 main 对应的 Pages 运行；“部署工作流成功”与“07 实际网页复测”仍分开。
- 更新唯一的 #20 正文，同时写入 Actions 运行摘要；不生成重复 Issue、不覆盖个人任务、不发通知刷屏、不合并 PR。

### 何时刷新

配置合并进 `main` 后：PR 检查开始/结束、Pages 检查开始/结束、main 推送、Issue 更新和 Issue/PR 会话评论会触发。PR 描述、草稿状态、关闭和正式评审变化通过无写权限的 **Submission events** 信号工作流触发，再由主分支汇总。它不检出或执行成员代码；Fork 仍受 GitHub 审批限制，旧分支可能尚无这个信号工作流。汇总可能排队或等待审批，成员可在原 PR 评论一句“交接信息已更新”，维护者也可在 [Actions](https://github.com/dinggegu-dot/wearwise/actions) 选择 **Team progress → Run workflow → main** 刷新。不设无人值守的聊天轮询，也不要求成员另填一张进度表。

Fork 首次运行可能要维护者批准原来的 CI；汇总不绕过审批。API 读取失败显示限制，完全读取失败保留上一份总览并让工作流失败；请看更新时间，旧快照不是实时结果。

### 权限和启用边界

写总览的工作流只运行主仓库 `main` 上的脚本，使用 GitHub 临时 `GITHUB_TOKEN`，权限为读代码/PR/检查/Actions及写 Issue；没有写代码或合并权限。它不执行 Fork 代码、PR 内容、评论中的命令或下载的构建产物，不使用 PAT、第三方服务或 AI API。仅专用 #20 正文带所有权标记时允许更新，评论不会被覆盖。

工作流文件需经用户批准合并后才能激活；PR 中通过测试不等于远程自动化已启用。唯一提交通道是团队交付约定；技术上是否能阻止所有人直推取决于仓库实际分支保护，文档本身不是保护规则。
