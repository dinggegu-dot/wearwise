# PR 提交与证据总览

成员按 12 轮排班和上一轮固定提交工作。正式成果通过团队 PR 提交；同一成果的返修更新原 PR。 [总计划 #10](https://github.com/dinggegu-dot/wearwise/issues/10) · [提交与合并指南](提交与合并指南.md) · [证据总览 #20](https://github.com/dinggegu-dot/wearwise/issues/20)

## PR 怎样填写

1. 标题写岗位号和轮次，例如 `[M02] 第 02 轮 数据服务`。模板保留「具体任务」「当前阶段」「验收项」「交付状态」「基线提交」「依赖 PR / 固定提交」字段。当前阶段填写实际轮次，验收项填写本轮真实覆盖的场景；纯文档可写「文档维护」。
2. 附当前候选完整 SHA、依赖关系、启动方法、操作证据、未执行项及接收者。上游仍未合并时，注明依赖分支与固定 SHA，核对差异是否包含前置改动。
3. 用 PR 和任务卡记录接口可联调、双方联调、独立验收及后续动作。完成者和接收者分别记录实际执行，合并后如需发布，再核对 Pages 和真实网页。

## 自动总览记录什么

`Team progress` 读取 PR、文件差异、提交 SHA、检查、评审和 Pages 运行，只更新 #20 的自动正文。PR 元信息变化由 `Submission events` 提供信号。#20 用于查找证据，验收结论以对应固定版本上的记录为准。遇到 Fork 工作流需要批准时，按 GitHub 正常流程处理。

**兼容限制。** 现有总览脚本的自动映射仍识别旧 A/B/C 阶段及 A01–A08 编号。填写新版轮次时仍可能出现字段提示；照实写本轮内容，并在任务卡和 PR 保留证据。脚本可继续展示 PR 与检查信息。按 12 轮自动聚合需要另行调整脚本。

总览写入任务从团队 `main` 读取脚本，使用 GitHub 临时令牌更新专用 Issue。它不执行 Fork 代码、PR 内容或评论中的命令。需要核对刷新状态时看对应运行和 #20 更新时间。 [Actions](https://github.com/dinggegu-dot/wearwise/actions) · [工作流历史验证记录](工作流验证记录.md)
